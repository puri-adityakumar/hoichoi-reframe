01Image path — two independent bugs, each fatal alone

The 9:16 story_image output contains a carved pillar and a floor. No people. The initial hypothesis was a single face-detection scale failure. That hypothesis is correct but incomplete — fixing it alone would not have fixed the 9:16. There is a second, independent bug in the crop scorer that zeroes the score of every face-containing candidate window.

Bug 1 · Face detection returns zero faces — a fill-fraction failure

worker/reframe/image/importance.py uses MediaPipe FaceLandmarker (running_mode=IMAGE, num_faces=6, min_face_detection_confidence=0.4) on an INTER_AREA copy downscaled to ANALYSIS_LONG_EDGE = 1600.

It is not a pixel-resolution problem and not a confidence-threshold problem:

ExperimentFaces found
Whole frame at 4000 / 3200 / 2400 / 1600 / 1200 / 1000 / 800 / 600 px 0 at every scale
min_face_detection_confidence = 0.4 / 0.2 / 0.05 / 0.01 0 at every value
1600 px copy upscaled 2× (bicubic / Lanczos / area) 0
Full-range detector (model_selection=1), 1600 px frame 1 — wrong model head, see below
Watermark removed / CLAHE applied / 2.6× gain (on a 600 px face crop) 1 — watermark and darkness are innocent
The actual mechanism

FaceLandmarker is hard-wired to the BlazeFace short-range head with a fixed-size input (FaceDetector: 192×192, per Google's own model card). A proposal is only ever generated if the face occupies roughly ≥13–15% of the frame.

Our two faces are 164×168 px and 152×164 px in a 4000 px master — 4.1% of frame, 3.5× below the floor. The variable that matters is the face's fill fraction, not its pixel size. Proof: holding the face at a constant ~180 px while varying only the frame size, detection dies exactly between 1300 px (13.8% fill, 1 face) and 1400 px (12.9% fill, 0 faces) — and the frontier is scale-invariant, so an 18 px face inside a 150 px frame is detected at 12% fill.

Only the scale at which we feed the model is a real lever: FaceDetector can be swapped to the full-range model, but FaceLandmarker cannot. Measured multi-scale results:

Strategy (on the 1600 px analysis copy) FacesFalse pos. Note
Single-shot 1600 px — what ships today 0—the bug
2×2 grid, 800 px tiles0— tiles too large
3×3 grid, 533 px tiles1 0loses one face
4×4 grid, 400 px tiles, 20% overlap2 0works, but 400 px sits on the 13–15% cliff
5×5 grid, 320 px tiles, 20% overlap 20 chosen — 66 px face in a 384 px tile = 17% fill, safely clear

The hard lower bound: do not go below ~300 px tiles. Two specific false-positive attractors were identified in this master — the carved ceiling motif at y≈0.076 and the blood pool at y≈0.625.

This is the bug that actually decided the crop, and it is independent of Bug 1.

Every 9:16 window with x ≥ 1600 — which is every window that could contain a face — scores exactly 0.0. Face A needs x ∈ [683, 1644]; face B needs x ∈ [1147, 1783]. The three candidates that were actually shipped sat at x ≤ 117: zero overlap, not even partial.

Bug 3 · Faces were a soft bonus, so nothing guaranteed they survived

# worker/reframe/image/crops.py
65  def _score(importance, face_mask, x, y, w, h, img_h):
79      if face_total <= 0:
80          return mean_imp          # ← silent. no log, no fallback.
82      return mean_imp + FACE_BONUS * inside   # FACE_BONUS = 0.3

Nothing anywhere rejects a crop that excludes every face. Note also that face_mask is (imp > 0.85) — a threshold of the fused importance map, not the detector's output — and it short-circuits before the face term is ever computed.

Bug 4 · The watermark band is unachievable for tall ratios

WATERMARK_BAND = (0.40, 0.60) is zeroed before faces are painted (faces are painted after, so a detected face survives the band — that part is correct). But measured: for 9:16, 1:1 and 4:5 cut from a square source, every candidate window at every zoom level the code uses must intersect that band, because such a crop is height-bound and spans nearly the full image height. The band is therefore a uniform 20%-of-height dead zone: it cannot steer the choice, it can only deflate all scores equally — while destroying the saliency of exactly the region the faces occupy. Face B (y 0.466–0.507) sits entirely inside the band.

Bug 5 · The VLM was right; it was given no way to say so

The recorded reason was:

“No people present; crop 1 frames the carved temple column and lit ground most completely and least cropped.”

The model correctly reported an empty candidate set, then applied the only criterion left to it — vlm.py:95 literally asks for the crop that “feels least cropped”. It had no escape hatch: the response schema is {"choice": int, "reason": str}, an out-of-range or unparseable answer is silently clamped to 0, and it only ever sees the 3 candidates it was handed. The fix belongs upstream in crops.py, not in the prompt — though the prompt has to stop rewarding emptiness too.

The uncomfortable implication

Three of four outputs were correct by accident. A judge spot-checking the gallery would very likely not catch this. That is worse than a visible bug, because it means the pipeline's correctness is not a property of the pipeline.

Test coverage that let all of this ship

  • test_importance_map_shape_and_range asserts imp.max() <= 1.0 — which passes just as happily on a map that is completely empty. It would pass on nothing at all.
  • test_candidates_916 never passes a face_mask, so crops.py:76-83 — the entire face-scoring branch — has zero coverage anywhere in the repo. The FACE_BONUS line is dead code on this master and no test noticed.
  • No test anywhere covers the zero-faces-found case.

Defect 1 · The no-active-speaker fallback is a non-speaker heuristic

video/camera.py:86-101 falls back to the mean centre-x of all visible faces (or the midpoint of the two widest if they fit in one window). This is a geometric heuristic wearing the costume of speaker tracking. Combined with defect 4 below it is what a judge reads as disqualifier #1.

It also produces the opening freeze: cur_cx is initialised to 0.5, so when no face is detected at t=0 the path begins with a literal centre crop — 2.80 s on clip_c, 4.40 s on clip_b.

Defect 2 · Two incompatible meanings of cx

# camera.py:150  — treats cx as a CENTRE POSITION ON THE FRAME
def _clamp(cx, crop_w):  return max(crop_w/2, min(1 - crop_w/2, cx))

# render.py:40   — treats cx as a FRACTION OF AVAILABLE TRAVEL
x_f = p["cx"] * (src_w - cw)

These agree only at cx == 0.5. The validator silently adopted the frame-centre reading, so it scores a window that was never rendered:

AssetValidator vs. render mean divergence Worst case
clip_c60.7 px208 px
clip_a58.1 px—

Two side effects: only 68% of the available travel is reachable, and the subject ends up pushed toward the frame edge (up to 16% off-centre) instead of centred — so a judge comparing the reel against the reported score sees a framing the score never described.

Defect 3 · The One Euro filter is completely inert

The clamp binds on 271 of 272 pan events on clip_a (99.6%). The filter's output is roughly 20× larger than the clamp, so camera.py:144 discards it on every single frame. MIN_CUTOFF = 0.8 and BETA = 1.5 have no observable effect whatsoever — all camera motion is a constant 152 px/s ramp. The code comment says “crosses frame in ~2 s”; measured, it takes 12.6 s, off by ~6×. There is also a first-sample passthrough bug: the filter returns raw unfiltered input on its first call, so after every shot-cut reset the first step is unfiltered.

The judges' toughest test explicitly inspects outputs for “cropped faces and violated safe zones”. A 24-term search for safe_area, title_safe, action_safe, subject_margin, forbid_face_clip, min_subjects_visible, eyeline, headroom, containment and 15 more across all first-party code returns zero rules.

The single most wasteful finding in this audit

We compute our own verdict on the hardest test, then throw it away

validate_speaker.py:96 computes an explicit boolean against TARGET = 0.85. Grepping all first-party code for a consumer of score['pass'] finds exactly one — a debug script. The pipeline scores 92.3%, and the UI shows a green bar with no threshold and no target marker (assets/[id]/page.tsx:51-61).

Worse, frames with active_track = None are dropped from both numerator and denominator, so 19 of 35 diarized segments on the master are excluded entirely and reported as score: null. The 92.3% is computed on the third of speech time where the system already knew the answer.

What is genuinely solid

Traceability — the disqualifier “outputs cannot be traced back to the master” — is not tripped and is the strongest non-AI part of the system. master_id is a non-null insert parameter (db.py:144-155), both call sites pass it, and there are four UI surfaces linking both directions plus a per-master library filter. Two gaps worth closing: the job page's local Output type drops master_id (jobs/[id]/page.tsx:8-15) so the natural first stop after upload shows no master link; and db/schema.sql is referenced by db.py:1-2 but is not in the repository.

Finding 1 — a published paper documents our exact bug, with a better detector

ClipsAI's own report, §Failure Cases, verbatim:

“The first is for faces that are small relative to the size of the image… Face detection models, being trained on images of a particular pixel width and height, often have trouble detecting faces who's pixel width and height are far outside their training data. … The face detection model fails to detect the speaker's face at all. As a result, the man to his left is chosen as a substitute in the absence of the true speaker's face being identified in that segment.”

That is an ICIP paper using MTCNN — a 3-stage scale-robust cascade, strictly stronger than our fixed-input landmark model — hitting our failure, documenting it in a figure captioned “Incorrectly chosen speaker due to small faces”, and not fixing it. That is a citable precedent, and it is the honest framing for our writeup.

Finding 2 — nobody validates semantics. This is our differentiator, not a gap

Not one of the five re-runs face detection on its own output. Not one checks a platform spec file. autoclip's entire post-render check is file.exists() and size > 0. There is no precedent anywhere in the reference set for what we are about to add — which is exactly why it is worth adding, and worth saying so plainly on the day.

Finding 3 — two citation errors in our own HANDOVER.md
  • ClipsAI is github.com/ClipsAI/clipsai, not clipsai/clipsai.
  • smartcrop.py is github.com/smartcrop/smartcrop.py (a community port). jwagner is the JavaScript original, jwagner/smartcrop.js. jwagner/smartcrop.py 404s.

Worth fixing regardless, because citing smartcrop.py as a face-aware cropper is a misreading of our own handover that a judge who checks would catch. It is a saliency prior.

Also verified: MediaPipe FaceDetector can be swapped to the full-range model, but FaceLandmarker cannot — so for our image path, tiling is the only available lever. That constraint is what fixes the remediation design.

05Stuck job e833ed33

A test job left at status='queued' with zero outputs. Root cause: the Blaxel worker never touched the row.

  • status='queued' is written in exactly one place in the entire repository — web/lib/db.ts:124. The worker's first database write is job_entry.py:129. A row still reading queued/0 therefore proves the container never reached line 129.
  • The complete Blaxel execution history in work/execs.json (11:45Z→13:52Z, no gaps) contains no execution carrying that job id.
  • web/lib/blaxel.ts swallows every failure mode — missing env at :9, any non-2xx at :26, timeout/TLS at :27 — and web/app/api/jobs/route.ts:28 discards the returned boolean entirely. Not logged, not persisted, not returned to the client.
  • worker/blaxel.toml:7 sets maxRetries = 0, so the platform will not retry either. The job page then polls every 2 s forever with no give-up condition, rendering Working… 0% indefinitely.
A structural defect that would hide the next occurrence too

job_entry.py:112-126 — load_config, _ensure_models, reading spec.json, get_master, mkdir — sits outside the try: that begins at line 128. Any failure in that window (missing secret, model fetch blocked, spec not uploaded, wrong Neon branch) kills the container before it can write failed. A boot crash is currently invisible by construction. Separately, the worker calls set_job but never finish_job, so finished_at is never set on worker-driven jobs.

Two things the harness caught that the unit tests could not

1. The reported number had to get worse

Active-speaker coverage is 32.2% on clip_a and 30.2% on clip_c — essentially unchanged from the 32.5% measured before the fix. What changed is that the headline metric no longer conditions on frames the system already got right. The old pipeline reported 92.3% while tracking a third of speech time; it now reports the all-frames figure and states coverage next to it.

This is a deliberate trade. The number a judge sees is lower and less flattering, and it is the number the code can actually defend.

2. Track consolidation is more conservative than the brief implied

Merging same-person fragments to a fixed point reduced the given master from 39 tracks to 39 — no merges fired. The fragments belonging to one person are separated by 2.4–7.6 s (a full reverse-shot), and neither a 7 s gap nor centre-distance alone justifies merging them without an appearance descriptor. The 11-and-8 fragmentation is therefore still present in the raw track list. What actually fixed the disqualifier is the one-to-one binding, not consolidation. Reporting this rather than claiming a fragmentation fix that did not happen.

On the degraded path

With no diarization — a Sarvam outage — coverage falls to 5.3% on clip_a and 2.0% on clip_c, and the ladder correctly spends its time in wide and hold rather than pretending to track. The mouth signal on these two clips is very weak: measured per-track contrast of 0.01–0.17 against a signal of ~0.17. The system now reports method="mouth-only" in the decision log rather than quietly producing a plausible-looking crop.

08Known gaps — stated, not hidden

This project already has an honest-failure philosophy: three validations on the video master fail in public (the 190 s reel exceeds Instagram's 90 s cap; two files exceed size limits). That is a genuine asset provided it is applied uniformly.

The asymmetry is the risk

We proudly fail the reel on duration while passing an image containing zero people 5/5. A judge who notices concludes the validator is a decoration — and the three honest failures stop reading as rigour and start reading as a demonstration of a failure state we already knew how to trigger. Credibility in an honest-failure system comes from uniformity, not from the number of failures.
